# S2: Exclusive output and gapless

Findings from live probing on 2026-10-07 (Windows 11 Pro 10.0.26200). Probe: `spikes/s2-audio` (`symphonia` =0.6.1 with `flac` + `isomp4`, `wasapi` =0.25.0), real-stream fetcher `spikes/s2-audio/fetch_segments.py`. Test media is generated by ffmpeg into `spikes/s2-audio/media/` (git-ignored); TIDAL segments were downloaded into `spikes/s1-auth/.secrets/` and deleted after probing.

```
cd spikes/s2-audio && cargo build --release
target/release/s2-audio formats                                   # exclusive format matrix
target/release/s2-audio play media/a.flac media/b.flac media/full.flac
target/release/s2-audio decode media/full_frag.mp4 media/full.flac  # fMP4 vs plain FLAC + seek
uv run --with httpx spikes/s2-audio/fetch_segments.py 328638758     # init + 3 segments (then delete!)
target/release/s2-audio decode ../s1-auth/.secrets/s2_328638758_init+3.mp4
```

## Device and accepted exclusive formats

Only render endpoint: **`Digital Output (FiiO USB DAC-E10)`** (USB, Windows class driver). Shared-mode mix format 96000 Hz / 2 ch / 32-bit float. Device period default 10 ms, minimum 3 ms.

Each format was checked with `AudioClient::is_supported_exclusive_with_quirks` (IsFormatSupported, EXCLUSIVE, WAVEFORMATEXTENSIBLE, mask 0x3; 24-bit is never re-queried as WAVEFORMATEX). Every accepted format was then really opened with `initialize_client(.., StreamMode::EventsExclusive)`. Exclusive mode never converts: a refused format is a hardware/driver limit.

| rate | 24-bit packed (3 bytes) | 24-in-32 (container 32, valid 24) | 32-bit int | 16-bit (extra) |
|------|------|------|------|------|
| 44.1 kHz | **accepted**, init ok (period 8.7 ms, 384 frames) | refused | refused | accepted |
| 48 kHz | **accepted**, init ok (9.3 ms, 448 frames) | refused | refused | accepted |
| 88.2 kHz | refused | refused | refused | refused |
| 96 kHz | **accepted**, init ok (10 ms, 960 frames) | refused | refused | accepted |
| 176.4 kHz | refused | refused | refused | refused |
| 192 kHz | refused | refused | refused | refused |

So this DAC (a 24/96 USB Audio Class 1 device) takes only 16- or 24-bit packed, at 44.1/48/96 kHz. **It cannot play TIDAL's HI_RES_LOSSLESS test track (24/88.2) bit-perfectly at all**, and the 192 kHz gapless pair could not be run (the probe stops with "device accepts no 24-bit-capable exclusive format"). The player must handle "source rate not supported by device" explicitly (see Recommendation).

## Gapless a→b test (96 kHz)

Source: a 6 s 1 kHz sine, 96 kHz, 24-bit FLAC (`full.flac`, 576000 frames), split mid-cycle at frame 288037 into `a.flac` (288037) + `b.flac` (287963), commands verbatim from the plan.

Setup: one WASAPI exclusive, event-driven stream, negotiated **24-bit packed, 96000 Hz, 2 ch, blockalign 6, mask 0x3, PCM**, period 10 ms (100000 hns, 128-byte aligned), buffer 960 frames. A decoder thread decodes a, then opens and decodes b, into a bounded channel of 4 packets (~170 ms), so b is opened while the device is at most ~4 packets ahead. That is the shape the real player will have. The render thread waits on the event, tops up from the channel without blocking, and writes one full buffer per event. The buffer is pre-filled before `Start`.

Underrun instrumentation (R3), counted on every event:
- **starved**: the device asked for N frames and fewer than N were queued while the decoder was not finished (the shortfall would be written as silence);
- **service > period**: the time from wake to `ReleaseBuffer` exceeded one period (deadline miss);
- **event timeouts**: no event within 1 s;
- also recorded: `GetCurrentPadding` at each wake (counts wakes with padding 0 while data remained), max event interval, and max service time.

Results (4 runs, identical):

| metric | value |
|---|---|
| UNDERRUNS (starved + late + timeouts) | **0** (0 / 0 / 0) in every run |
| frames written vs `full.flac` | 576000 vs 576000 |
| sample equality (every i32 sample, count and values) | **SAMPLE-EQUAL=true**, asserted in code |
| padding at wake | always 960 (one full buffer still queued). Never 0. |
| max event interval | 15.1–15.3 ms (one late wake). It was still covered: a full buffer (10 ms) was queued at every wake. |
| max service time | 0.46–0.48 ms (deadline 10 ms) |
| opening b (probe + decoder) | 144 µs on the decoder thread |
| wall time / device clock | 6.026 s / 6.010 s |

Notes:
- In exclusive event mode, `wasapi`'s `get_available_space_in_frames()` returns the whole buffer, and `GetCurrentPadding` read at wake equals the buffer size (the other half of the ping-pong is playing). So "padding 0 while data remained" is the real starvation signal; it never fired.
- Written bytes come straight from symphonia's left-justified i32 (FLAC N-bit samples are shifted to the MSBs; asserted: the low 8 bits are always zero). Packed 24 = bytes 1..4 of the little-endian i32. 24-in-32 / 32-bit would be the i32 bytes as-is (WASAPI valid bits are MSB-aligned). Both are lossless for content of 24 bits or fewer.
- The tone was played through the DAC. Nobody listened to it during this run; listening is optional and left to the human.
- The `wasapi` docs warn that event-driven exclusive mode can stutter with the Windows USB class driver. This USB DAC showed no underruns. Keep `PollingExclusive` as a fallback mode if users report stutter.

## fMP4 FLAC decode with symphonia 0.6.1

### (a) Synthetic

`ffmpeg -i full.flac -c:a flac -sample_fmt s32 -bits_per_raw_sample 24 -f mp4 -movflags frag_keyframe+empty_moov+default_base_moof -frag_duration 1000000 full_frag.mp4`. No `-strict -2` was needed with ffmpeg 9. `-frag_duration` was added because `frag_keyframe` alone wrote a single `moof` for audio. With it the file is `ftyp moov (moof mdat)x6 mfra`.

Decoded as one forward-only byte stream (`ReadOnlySource` over the file): 96000 Hz, 2 ch, 24 bit, **576000 frames, 0 decode errors, SAMPLE-EQUAL=true vs the plain-FLAC decode of `full.flac`**.

### (b) Real TIDAL stream (track 328638758, HI_RES_LOSSLESS)

`playbackinfo` → `audioQuality HI_RES_LOSSLESS, bitDepth 24, sampleRate 88200`. The MPD has Representation `FLAC_HIRES,88200,24`, codecs `flac`, timescale 88200, startNumber 1, 69 segments, `d=352256` frames each (3.994 s = 86 FLAC frames of 4096), last 259256, total 24212664 frames = 274.52 s (matches `PT4M34.52S`). Structure of the downloaded bytes:
- init segment: 619 bytes, `ftyp` + `moov` (`mvex` with `mehd` + `trex`; `mdhd` timescale 88200);
- each media segment: exactly one `moof` + `mdat` (~1.2 MB), no `styp`/`sidx`. `moof` has `mfhd seq=k` and `tfdt` v0 with `baseMediaDecodeTime` = cumulative frames (0, 352256, 704512), `trun` flags 0x201 with 86 samples.

init + segments 1–3 concatenated (3.73 MB) and decoded as ONE forward-only byte stream:

| | |
|---|---|
| sample rate / bit depth / channels | **88200 Hz / 24 bit / 2** |
| decoded frames | **1056768** (exactly the sum of the 3 segment durations in the MPD) |
| decode errors | **0** |
| bit-exactness | FNV-1a64 over s32le samples `11a92ee3bd2faacc`, **identical to `ffmpeg -f s32le` of the same bytes** |
| speed | the whole `decode` command (probe + 12 s of audio + 4 re-opens + seeks) took 55 ms wall in a release build |

Further facts the player depends on:
- `Track::num_frames` is `Some(0)` for fragmented MP4 (no duration in `mdhd`). Take the duration from the MPD or playbackinfo, not from symphonia.
- **symphonia 0.6.1 ignores `tfdt`.** `MoofSegment::new` derives a fragment's first timestamp from the previous segment's end. A stream built from init + segment 3 only decodes 352256 frames that are **sample-equal** to segment 3 of the continuous decode, but its pts start at 0, not 704512. FLAC frames are self-contained, so starting at any segment is clean. The caller must add the segment's start time (sum of earlier `S@d` = `tfdt`).

### Seek

`FormatReader::seek(SeekMode::Accurate, SeekTo::Timestamp)` followed by `decoder.reset()`. Each result below was checked by comparing the first packet after the seek with the linear decode at that pts.

| source | seek | synthetic (1024-frame packets) | real TIDAL (4096-frame packets) |
|---|---|---|---|
| seekable `File` | forward to 50% | required 288000 → actual 287744, samples match | required 528384 → actual 528384, match |
| seekable `File` | then backward to 10% | 57600 → 57344, match | 105676 → 102400, match |
| forward-only `ReadOnlySource` | forward to 50% | works, match | works, match |
| forward-only `ReadOnlySource` | then backward | `seek` returns Ok, but the next packet fails: `isomp4: out-of-bounds seek for a non-seekable stream` | same |

So symphonia can seek within the concatenated stream. Accurate mode lands on the packet start at or before the target, so a sample-accurate seek must discard `required - actual` frames after decoding. A forward seek on a forward-only source just reads and parses `moof`s until it reaches the target, which costs downloading every byte in between. A backward seek needs a seekable source.

## macOS (desk research: coreaudio-rs 0.14.2, not run)

Bit-perfect exclusive output on macOS needs hog mode. cpal 0.18.2's CoreAudio host sets the physical format and nominal rate itself (`set_physical_format`, falling back to `set_sample_rate`), but it never takes hog mode, so other apps can still mix into the device or change its rate. Use `coreaudio-rs` directly. The call sequence comes from `coreaudio-rs` `examples/sine_advanced.rs` and `audio_unit/macos_helpers.rs`:
1. `get_default_device_id(false)` (or `get_device_id_from_name`) gives an `AudioDeviceID`. `get_hogging_pid(id)`: -1 means free. `toggle_hog_mode(id)` returns the new owner pid. Check that it equals `std::process::id()`. Release it with `toggle_hog_mode` again on stop. The OS also releases it when the process exits.
2. `get_available_sample_rates(id)`: if the source rate is missing, the device cannot play it bit-perfectly. Optionally call `set_device_sample_rate(id, rate)` (sets `kAudioDevicePropertyNominalSampleRate`, waits up to 2 s for the `RateListener` to confirm). The next step changes the rate anyway.
3. `find_matching_physical_format(id, StreamFormat { sample_rate, sample_format: I24 or I32, channels: 2, .. })` returns an ASBD. `set_device_physical_stream_format(id, asbd)` sets `kAudioStreamPropertyPhysicalFormat` and polls until the device reports it (2 s timeout). `StreamFormat` covers only a few formats; packed 24-bit needs a hand-built ASBD (`SampleFormat::I24` + flags).
4. `audio_unit_from_device_id(id, false)` gives the AUHAL output unit. `set_property(kAudioUnitProperty_StreamFormat, Scope::Input, Element::Output, asbd)` sets the client format. `set_render_callback(..)`, then `start()`.
5. Register `RateListener` and `AliveListener` to detect another process changing the rate or the device disappearing.

The AUHAL converts the client format to the device's virtual format, usually Float32. Converting int24 to float32 and back is exact (24-bit significand) as long as nothing scales the signal (unity volume, no effects). Verify this on hardware. A 32-bit source would not survive the trip (TIDAL is at most 24-bit).

## Linux (desk research: cpal 0.18.2 ALSA host, alsa 0.11, not run)

Call sequence: `cpal::host_from_id(HostId::Alsa)` → `host.device_by_id(&DeviceId::new(HostId::Alsa, "hw:CARD=X,DEV=0"))` (the id is canonicalised, so `hw:1,0` → `hw:CARD=1,DEV=0`; enumeration lists `hw:`/`plughw:` per card) → `device.supported_output_configs()` → choose an entry with the exact rate and format → `build_output_stream_raw(&StreamConfig { channels: 2, sample_rate, buffer_size: BufferSize::Fixed(period) }, sample_format, ..)` → `play()`. Internally cpal opens the PCM non-blocking and applies these hw_params: `RWInterleaved`, format, `set_rate(rate, ValueOr::Nearest)`, channels; `Fixed(n)` gives period n and buffer 2n. sw_params: start threshold 2 periods, avail_min 1 period. Pitfalls found in the source:
- **`set_rate` uses `ValueOr::Nearest`.** On `hw:` an unsupported rate is silently replaced by the nearest one, and there is no resampler, so playback would run at the wrong speed. Always pre-check the exact rate in `supported_output_configs()`. That list probes discrete rates via `test_rate`.
- **cpal's `I24` is ALSA `S24_LE`**: a 4-byte container with the 24 bits in the low 3 bytes (LSB-aligned, so shift the left-justified i32 right by 8). **Packed `S24_3LE` is not supported by cpal** (commented out in its format table). Many USB DACs on `hw:` expose only `S24_3LE` and/or `S32_LE`. This FiiO only accepted packed 24 on Windows, so through cpal it would get 24-bit only if it also offers `S32_LE` (send the left-justified i32 as is, which is bit-perfect). Otherwise there are two routes. One is `plughw:` after confirming the exact rate on `hw:`: plughw then only converts the container, which is lossless, but it would also resample silently if the rate were wrong. The other is the `alsa` crate directly (already a cpal dependency).
- `hw:` has no mixer. If PipeWire/PulseAudio holds the card, opening fails with `DeviceBusy`. The cpal README says to use the `pipewire` host or `pulse` bridge then, and neither is bit-perfect unless the server's rate is pinned. Surface this to the user.
- `BufferSize::Default` on ALSA can be huge; always use `Fixed`.

## Recommendation for the player crate

**Decode path (DASH fMP4 FLAC):** symphonia 0.6.1, features `flac` + `isomp4`, is sufficient and bit-exact. A remuxer and a separate FLAC demuxer are not needed.
- The player takes each track as a forward-only byte stream (`Box<dyn Read + Send>`: init segment bytes, then media segments in order), wraps it in `ReadOnlySource` → `MediaSourceStream` → `get_probe().probe` → `make_audio_decoder`. This keeps `player` free of HTTP and `tidal` types. The app layer adapts TIDAL segment downloads into the `Read`.
- The track descriptor passed with the stream carries sample rate, bit depth, duration (from the MPD/playbackinfo, since symphonia reports `num_frames = 0`) and `start_frame`.
- **Seek = restart the stream at a segment.** Pick segment k from the SegmentTimeline (start frame = sum of earlier `d`), feed init + segments k.., add `start_frame` to every pts (symphonia ignores `tfdt`), and drop `target - start_frame` frames after decoding. Use symphonia's own seek only for short forward hops.
- Gapless: one decoder thread decodes track after track into a bounded queue feeding one open output stream. The next track is opened when the current one hits EOF (probe + decoder took 144 µs). This is exactly what S2 verified: 0 underruns, sample-equal.
- Keep samples as left-justified i32 end to end. Convert to the device container only at the output (bytes 1..4 for packed 24, as is for 24-in-32/32, `>> 8` for ALSA `S24_LE`). Never go through f32 on Windows or Linux.

**Output path per OS:**
- **Windows:** `wasapi` 0.25 exclusive, event-driven. Negotiate with `is_supported_exclusive_with_quirks` in the order packed 24 → 24-in-32 → 32 (16-bit sources may also use 16), then `initialize_client(EventsExclusive { period })`. Use the default period aligned to 128 bytes, with the `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED` retry. Pre-fill before `Start`, write the whole buffer on each event, and keep the S2 underrun counters as runtime telemetry. Keep a `PollingExclusive` fallback for USB class-driver stutter. Gapless holds only while consecutive tracks share rate and bit depth. A format change means stop and re-initialize, which is an unavoidable short gap.
- **macOS:** `coreaudio-rs` 0.14 directly, not cpal: hog mode, nominal rate, physical format, AUHAL with an f32 client at unity gain. Needs an on-hardware bit-exactness check (desk research only so far).
- **Linux:** cpal 0.18 ALSA on `hw:` with an exact-rate pre-check and `BufferSize::Fixed`. Expect to drop to the `alsa` crate for `S24_3LE`-only USB DACs.
- **All OSes:** when the device lacks the source rate (as with this DAC and 88.2 kHz), do not let the OS convert silently. Either resample explicitly (rubato) and mark playback "not bit-perfect" in the UI, or let the user choose shared mode. Decide in the player spec. S1's hi-res test track is 24/88.2, and 88.2 kHz is missing on many 48/96 kHz-family USB DACs, so this case is not rare.
