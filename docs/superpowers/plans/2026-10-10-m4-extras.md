# M4 Extras Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the v1 scope: playlist editing, folders and reordering; track and artist radio; synced lyrics and credits; Last.fm and ListenBrainz scrobbling; Discord Rich Presence; tray with close-to-tray and start minimized; single instance with `tidal://` links; the rest of Settings (account with the client ID override, behavior, integrations, theme, shortcut list).

**Architecture:** `tidal` gains lyrics, credits, mix ids, and playlist and folder writes. The writes mirror official client 2026.09.30: v1 item writes guarded by the playlist's ETag, v2 folder PUTs, and openapi JSON:API for creating and editing playlists. `app` gets a library tree (folders plus the user's own playlists) in the model, refreshed after every edit. A right panel shows Queue, Lyrics or Credits. Scrobbling runs on the backend: `Playback` signals "now playing" and "scrobble due" (the time-based rule) over its `Msg` channel, and a `Scrobbler` sends to Last.fm and ListenBrainz with a disk queue for retries. Discord presence and the tray are UI-side, like the existing media controls. The app moves onto `fastframe-shell`, so it lives on headless in the tray. `fastframe-instance` hands a second launch's link to the running app.

**Tech Stack:** Rust 2024, egui/eframe 0.36 on fastframe v0.4.1 (adds `fastframe-tray`, `fastframe-shell`, `fastframe-instance`), tokio, reqwest 0.13 (rustls), serde, `md5` 0.8.1, `discord-rich-presence` 1.1.0.

**Spec:** `docs/superpowers/specs/2026-10-07-tidash-design.md` (§3, §6, §7, §8, §9, §12, §13 M4). The research behind this plan is in two notes in the session scratchpad: `m4-endpoints.md` (official client 2026.09.30 and 2026.10.08 bundles, python-tidal, SONE, live GETs) and `m4-integrations.md` (fastframe v0.4.1 sources, Spotifast `5b7a5df`, Last.fm, ListenBrainz and Discord specs). The scratchpad is not kept: Task 1 folds `m4-endpoints.md` into the S5 spike doc, and each task's brief quotes what it needs from `m4-integrations.md`.

## Review Focus

1. **A playlist changed elsewhere (stale ETag, 412) while the user edits it.** An add is retried once with a fresh ETag. A remove or move is not retried: the user is told, and the page reloads. The wrong track is never removed. Tests: Task 3 `add_retries_once_on_412`, `remove_on_412_is_not_retried`; Task 7 `a_412_reloads_the_playlist`.
2. **Playlists that hold videos or unavailable tracks.** Remove and move address the item's position in the playlist, not the row's index on screen. Tests: Task 3 `playlist_items_keep_positions_past_videos`; Task 8 `remove_sends_the_playlist_position`.
3. **Scrobbling while offline, while the service is down, or after the user revoked the app.** Due scrobbles go to the disk queue and are sent later, oldest first, with none lost or doubled. A revoked session shows one "reconnect" notice and keeps the queue. Tests: Task 9 `failed_scrobbles_persist_and_flush_in_order`, `invalid_token_keeps_the_queue_and_asks_once`; Task 10 `error_codes_map_to_retry_reconnect_or_drop`.
4. **Pausing, seeking, skipping and repeat-one around the scrobble threshold.** One scrobble per play, once the time actually played reaches min(half the track, 4 min). Tracks of 30 s or less never scrobble, and a repeat counts again. Tests: Task 9 `due_rule`, `one_scrobble_per_play_and_a_repeat_counts_again`.
5. **Malformed or hostile links from a second launch** (`tidal://track/1%2F..%2Fusers`, an unknown kind, a foreign host, a 20 KB argument). These are ignored and never reach an API path. A valid link opens once logged in. Tests: Task 13 `parse_rejects_hostile_input`, `a_link_waits_for_login`.
